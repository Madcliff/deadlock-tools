# Deadlock modding findings

These findings describe the Unity 2018.4 Deadlock files inspected during development. Check the exact build and selected files before applying a patch. Test a candidate mod in a local skirmish before using it in a campaign.

## What each file controls

| Source | Data observed | How to inspect |
|---|---|---|
| `BSG_Data/level*` | Ship records, build costs, slot totals, research, fleet limits, and commander tables. Multiple scenes carry copies. | `shipdb show`, `shipdb fleetinfo`, `shipdb commanders`, and the Database page |
| `sharedassets9.assets` | Squadron hull pools, fighter counts, and fighter-loss thresholds in the inspected files. | `shipdb squadrons` |
| Ship bundle | Unity prefab components, weapon mounts, attached ship systems, launch actions, bay positions, and battle menus. | `weapons BUNDLE --inspect` |
| `Assembly-CSharp.dll` | Rules that interpret prefab settings, battle actions, and campaign saves. The database tool also reads managed metadata to decode level tables. | `dll check` |
| `battle_shared` | Shared assets referenced by ship prefabs, including the Deploy Plating drone. | Inspect the serialized CAB object and the ship bundle's external references and preload table |

The modded Mercury was observed with level values of 200 hull and armour values of 180 front, 100 rear, 140 port and starboard, 100 top, and 120 bottom. Its modified prefab showed 800 hull and armour values of 720, 400, 560, 560, 400, and 480. The apparent 4× relationship was a mismatch in the modded data, not an intended conversion. The editor now treats corresponding level and prefab hull/armour values as 1:1, flags mismatches, and lets the user choose either file as the source. Applying the correction writes the selected values into the other file in the work tree. The full list of shared values is in [game/bundle-level-agreement.md](game/bundle-level-agreement.md).

## Managed DLL patches

| Patch | What it changes | Related data |
|---|---|---|
| Armour regeneration (removed) | Added armour restoration scaled by the hull repair rate and a factor. | Older bundles flagged it with a negative `RegenerativeHullResinModule.hullPerTick`. Replaced by `CustomArmourRepairModule`; saving a bundle with that module flips the rate back to positive. |
| Squadron revive (removed) | Let a flagged ship's Munition Factory rebuild destroyed squadrons. | Older bundles flagged it with `ShipInfo.ShowExclusionInEditor = 1`. Replaced by `CustomSquadronReplacementModule`; saving a bundle with that module clears the flag. |
| Munition load | Extends the load-time check so a saved munition list shorter than the configured slot total is rebuilt. | Level records set the slot total, and the prefab supplies battle launch actions. Review existing loadouts after loading. |
| Indexed turnaround repair actions | Uses unique IDs starting at 60 and increments by radial-menu position. | The tool adds matching `KeyManager.Mappings` and `MappingsAZERTY` rows in `level3`, plus localized descriptions in `resources.assets`. The custom DLL adds a matching native launch-slot widget per repair module. |
| Commander rank cap | Changes the maximum rank used by the game. | Extend the commander rank and XP tables separately. |
| Command nodes | Adjusts the hard-coded command-node count and rank spacing. | The command-tree display and commander data should be tested together. |

The DLL tool checks expected byte patterns or offsets before editing. Unsupported builds can fail even when the managed class names match. Staged patches build on the output DLL by default. Use `dll check PATH` to inspect the installed DLL specifically. Repair action positions 4 onward map to unique shortcut IDs 60 onward; the KeyManager and localized key-name assets must be staged with the DLL for keyboard input and labels to work.

Four experimental module classes (armour repair, destroyed-squadron replacement, drone plating resupply, and magazine capacity) were merged into a candidate DLL from the current GOG install. The user identified that the eGPU had been unplugged when the crash occurred; the crash report stops during D3D11/DXGI initialization (`d3d11: failed to create factory`), before managed assemblies load. On 2026-11-21, the candidate DLL and Mercury bundle were reinstalled for a post-reboot test. Their hashes match the preserved candidates at `work/.deadlock-backups/custom-modules-install-20261121/`; the pre-install files remain backed up in the GOG install's `.deadlock-backups/custom-modules-install-20261121/`. Steam was not modified. The candidate DLL had passed a prior Proton startup smoke check, but the module behaviors remain untested in battle. `scripts/build_custom_modules.sh` builds candidates into the configured work overlay. Drone resupply writes the private `DeployPlatingModule` reserve field and is tied to the inspected game build.

The installed GOG `BattleSimulation` constants are `SimulationTicksPerSecond = 10`, `SimulationTickDuration = 0.1`, `SimulationTicksPerRound = 120`, and `SimulationLengthInSeconds = 12`. The custom-module editor now derives per-second values using 12 seconds per round. Playback speed can affect wall-clock timing; the 120-tick round count is the stable in-game progress basis.

The ship bundle writer creates MonoScript and MonoBehaviour records for the four custom modules using the bundle's existing Unity 2018.4 MonoBehaviour header, appending each module's scalar settings and calculating its script/type hashes. The generated Mercury bundle reopened successfully in the tool and is installed to the GOG game's `BSG_Data/StreamingAssets/colonialmercury` for testing. It preserves the six munition actions, eight squadron actions, Munition Factory, Armory range (25–100), and inspected abilities. It attaches all four custom components, changes Hull Resin to positive hull-only repair, and clears the ShipInfo flag used by the legacy squadron revive hook. The drone module's base rate is zero, so it will not restore plating until configured. Bundle parsing and round-trip succeeded; in-game loading and module behavior await the post-reboot test.

The ship editor now recognizes the four custom module classes and exposes their rate/multiplier, modifier-rate, and crew-veterancy selector fields. The selector uses the supported game's `FEDNAJLFKEF` values. These editor fields become visible when the matching component exists in a bundle; this does not itself add the components.

`ShipInfoPanel` serializes one `RepairBaySlotButton`. The DLL candidate now clones that native widget under the same parent for each additional module, assigns indexed shortcut functions, and refreshes each button against its own module. `TurnaroundRepairBayAction` now selects its module by its component index on the Fighters menu, paired with the module's index on the ship. The bundle writer creates one module and one action per configured repair bay, including reconciling the existing Mercury bundle's two actions with its previously single module. `TurnaroundRepairBayAction.get_VisibleInShipInfoPanel` remains hidden so repair controls stay in the launch-slot row instead of the generic ability stack. The earlier generic-stack visibility change was removed on 2026-11-21 after a backup was made at `.deadlock-backups/repair-slot-ui-correction-20261121/Assembly-CSharp.dll`.

The magazine-capacity module hooks the two vanilla paths that otherwise ignore its multiplier: `ShipInfo.GetMunitionsSlotStatusData` (reported slot maximum) and `ShipInfo.ResupplyMunitions` (resupply clamp). The module also scales the starting load. Vanilla `MissileDataTableObject.MaxMissiles` values remain untouched. The combined candidate `work/candidates/Assembly-CSharp-repair-slots.dll` was installed to the GOG DLL and Mercury bundle on 2026-11-21; matching SHA-256 hashes were confirmed in the work and GOG paths. Both bundles contain two repair modules and two Fighters actions. The new repair buttons, independent bay behavior, and magazine HUD/resupply behavior still need an in-game battle check.

Experimental EMP uses the game's `BattleManager.GetShipTargets` radius query and subsystem `AddMaxHealthEffect` path. Activating it queues the action for `StartSimulation`; `detonationDelayTicks` can delay the pulse further using the tick event. The query must set `includeCapitals=true`; otherwise battleships are silently excluded before the team/faction filters run. The same game query also rejects every `IsChild` ship, which excluded fighter craft. EMP target collection now supplements the radius query with BattleManager's complete ship list, then applies its own active, enemy-team/faction, and blast-radius checks so child fighters can be affected. Each detonation reports the number of squadrons stunned and fighters jammed, in addition to enemy targets and missiles, making the result visible in the battle notification. Jamming sets the target `ShipInfo.IsJammed` flag, which routes through `DataTables.JammingPenalty` and applies its native evade penalty. Setting `subsystemDamage` to zero disables the subsystem effect without disabling missile destruction or fighter effects. Active missiles are registered separately with `MissileEventProxy`; they are not in `BattleManager.NonShipDestructables`, which caused the original EMP missile scan to miss them. The EMP reads the proxy's live missile list, falls back to active missile scene objects, checks the launching ship's team and faction, and destroys only in-range enemy missiles. The module uses the game's tick event to restore temporarily disabled enemy squadrons after the configurable `disableSquadronTicks` duration (360 by default). Defaults are 1,000 units, one turn between uses, 8 subsystem maximum-health reduction for 240 recovery ticks, and a 360-tick fighter stun. Instant Plating similarly queues activation for `StartSimulation`, with an independent configurable `activationDelayTicks`. Both delays default to zero. The editor and Mercury bundle expose these settings. The previous candidate's radius query excluded capital ships, explaining why subsystem damage appeared not to work against the tested battleships.

Targeted EMP uses one per-turn charge for each activation. Each activation opens one native PCM-style 3D selector; the player can repeat the action up to `chargesPerCooldown` times to queue independent locations. Charges reset at the end of each simulation turn. All queued locations fire at the next `StartSimulation`, after the configured delay, with separate bursts spaced by `burstIntervalTicks` (default 10 ticks / 1 second). Keeping the selector callback and charge state on the persistent ship module avoids depending on a transient ship-action object surviving input-context changes. This replaces the unreliable multi-selection-in-one-action flow. The targeting range defaults to 4,000 units; the blast radius defaults to 1,000. Each burst uses the shared EMP subsystem damage, fighter stun, enemy missile destruction, and fighter jamming logic. Fighter jamming sets the target `ShipInfo.IsJammed` flag, which routes through `DataTables.JammingPenalty` and applies its native evade penalty. The vanilla Cylon Virus Mine defaults to 360 ticks (three turns) for its hacking/jamming field. EMP fighter jam and stun default to 360 ticks and remain configurable (`fighterEvadeDebuffTicks` and `disableSquadronTicks`). Vanilla EMP Mine subsystem recovery is 240 ticks (two turns); this is distinct from fighter-stun duration. Existing EMP module schemas retain the inherited cooldown field for serialization compatibility, but Targeted EMP uses per-turn charges instead. In-game activation and detonations still need a battle check.

The 2026-11-21 fighter-duration update sets stun and evade-jam to 360 ticks (three turns), matching the vanilla Cylon Virus Mine jamming-field duration. The build is `work/candidates/Assembly-CSharp-emp-fighter-jam-360ticks.dll`; it includes the 32,000-point choice in skirmish PvP and co-op cap lists without changing the default. The DLL (SHA-256 `2bb49a653e2627ce5d2bf985dcd86214719b18b49bc79bdb7a3ddbc889cb6d06`) and Mercury bundle (SHA-256 `c8e31fd5f78f491a02aefebffcec6aa0057e10df36c07abdf8b8b06a1e3c0cc0`) were installed to both the work overlay and GOG install. Each prior DLL and bundle is backed up under `BSG_Data/.deadlock-backups/emp-fighter-duration-360ticks-20261121/`. The editor archive was rebuilt as `dist/deadlock.pyz` (SHA-256 `06b9174feb5c98a6884f9f1a097e474356d7f64273e0b033d4034d4ff44967668`). In-game verification of the fighter jam/evade penalty, targeting, EMP damage, missile destruction, and fleet-cap option remains outstanding. The game's `IsJammed` flag affects combat calculations but does not show a custom EMP duration/countdown badge; a fighter status indicator remains a useful follow-up.

### Patching a custom-module build

The custom-module build (`scripts/build_custom_modules.sh`) rewrites `Assembly-CSharp.dll` with Mono.Cecil. Cecil
lays the method bodies out anew and stores identical bodies once: in the November 2026 build,
`TurnaroundRepairBayAction.get_VisibleInShipInfoPanel` shares its `ldc.i4.0; ret` body with four other methods. So
the patches that work at fixed file offsets of the stock build (the indexed repair-bay shortcut) must never touch a
rebuilt DLL, and an in-place body edit there could change unrelated methods. The merge script installs the indexed
shortcut itself (`get_ShortcutKey` returns 60 + radial position − 4), so `dll` treats a DLL that contains the custom
module types as a custom build: `check` reads `get_ShortcutKey` through the metadata and reports it as built in,
`patch --repair-bay-actions` only stages the key mappings, and a revert of everything leaves the built-in shortcut
alone. Rank, command-node and munition-load patches find their sites by byte pattern and still apply.

## Bundle editing and dependencies

### Commander skill trees

The level DataTables hold subsystem-to-ability choice arrays, `CaptainSkill` definitions, and `CommanderSpecialisationBonusAmount` values. The Commanders page reads all ability records in the configured level data, reallocates subsystem choices, edits bonuses/display/localization metadata, and provides separate scroll areas for the tree, choices, and ability list. Each ability can be assigned an unlock rank. The game DLL originally uses a three-entry, slot-indexed rank array; the per-ability hook now also handles branches with more than three choices, falling back to the last vanilla gate for additional entries. This matters for the GOG CIC branch, which has four choices (including `Gift of Olympus`); without the hook its fourth choice indexes beyond the game's three rank gates and can prevent the branch from rendering. The editor now builds that hook automatically when a saved branch has more than three choices, even if no custom unlock rank was assigned. Rank assignments are saved in `.deadlock-tools/commander_ability_levels.json`. The shared Command-column node schedule remains controlled separately by DLL settings. The editor can create custom flat or percentage modifiers for native ship-stat paths; each gets a unique serialized ID, a bonus row, localized title/description strings, and a matching DLL stat hook. Economy, leadership, and XP effects are not exposed as custom stat modifiers. Saves update matching level tables and work-tree DLL/resources files with backups. New abilities and their presentation still need an in-campaign check.

The tool reads the game's XOR-wrapped UnityFS bundles and the serialized type trees inside them. An ability transfer can require several pieces: a serialized module, its action component, a free menu position, ownership links back to the correct GameObjects, and external assets. A copied reference may exist in the file and still be unresolved in Unity if the prefab's preload metadata omits its dependencies.

### Deploy Plating

- Stock donor values observed in Celestra were 400 total supply, 40 per drone load, 50 maximum plating, application rate 0.2, and deployment range 750.
- Mercury's battle log recorded accepted Deploy Plating commands followed by a null argument to Unity's drone prefab instantiation. The object existed in the installed `battle_shared` CAB. The initial transfer had omitted its external preload entries.
- The repaired transfer carries the donor's matching external preload dependencies and updates the prefab's preload window. A comparison of the repaired Mercury verified the shared object references and preserved the other prefab objects and resource bytes.
- The inspected DLL's initial plating target filter permits the owning ship if it satisfies the usual eligibility checks. That static finding does not establish that the complete selection and drone sequence succeeds in battle.

### Carrier slots and display

The database supplies fighter and utility counts. The prefab contains the actual launch actions, bay compatibility, and optional icon transforms. Keep these in agreement. Slot IDs start at zero, with fighter slots before utility slots. The inspected installed Mercury had five fighter slots and one utility slot, but some fighter positions pointed to support-only bay compatibility lists. The staged correction aligned the lists while retaining a Raptor-compatible utility bay and moved the two extra icon markers. The build and deployment screens still need visual verification for a given configuration.

The installed Mercury bundle can also have a full Fighters radial menu. Adding the turnaround repair action alone then fails for lack of a free position. A staged rebuild using the level record's 5 fighter and 1 support slots, grouped into separate 5/1 submenus, created six launch actions and bays and added the repair action successfully. This is a prefab-level validation; confirm icon spacing and the campaign build/deployment presentation in game.

### Creating a new ship

The Ships page now has a “Copy and add a ship” workflow. It clones an existing ship record into every configured ship table, assigns a new ID and localized name/blueprint strings, copies a selected donor bundle into the merge-ready StreamingAssets work tree, and adds the record to a selected campaign research list. It registers that ID in `FleetModelFactory`, `ProjectionFactory`, `ShipImageDataTable`, and the battle `ShipFactory`, and in the working DLL's `ShipType` enum. `ShipFactory` maps a ship type to its battle bundle name; without that record the ship can be selected and configured in Skirmish, but battle logs `Template '<ShipType>' not found` and does not spawn the ship. The enum value is required because fleet placement builds its collision-radius dictionary by iterating enum values; a ship row with an unregistered ID throws `KeyNotFoundException` when added. The enum is obfuscated (`NDBFKAOICBG` in the inspected build); find it by its `ColonialBattlestarMercury = 29` member. Vanilla has 68 members (highest 205), and every vanilla ship-table row has one. Any DLL rebuilt from a clean copy loses the members added for copied ships. On 2026-11-23 the custom-module rebuild started from `work/.deadlock-tools/base/Assembly-CSharp.dll` (made before the MK2 was added), so `ColonialBattleshipMercuryMK2 = 206` disappeared from the installed GOG DLL and the work DLL, and adding the MK2 in Skirmish threw again. On 2026-11-24 the member was restored to both DLLs with backups under `.deadlock-backups/shiptype-206-restore-20261124-120258/`; types, methods and `dll check` output were otherwise unchanged. The custom-module rebuild and fresh DLL patches now carry ShipType members over from the DLL they replace, and give any ship-table ID still missing one a `CustomShip<id>` member. The donor's ship settings, ability fields, attachment arrays, veterancy, image references, and preview art reference are retained. Because the runtime requests `LoadAsset<GameObject>(assetName)`, copying a bundle also renames its internal AssetBundle name, prefab container path, and referenced prefab root to the new lowercase factory key. This does not generate new art, prefab geometry, or mount/shared-asset references.

The first Colonial Mercury MK2 copy had Mercury's ship fields, slot counts, research entries, and a bundle file, but still failed to spawn. The GOG game log showed it opened `colonialmercurymk2`, then reported `Main asset is null, or not a game object! (Colonial Mercury MK2)`. The level factory pointer and filename matched, but the copied bundle's internal AssetBundle name and prefab container path still identified the original Mercury (`colonialmercury` / `assets/_prefabs/ships/colonialmercury.prefab`). Deadlock requests the prefab using the factory key as its asset name, so Unity returned null. The clone code now changes the internal AssetBundle name, container key, and referenced root GameObject to `colonialmercurymk2`. The ship then appeared, but its in-game record still identified it as Mercury because the copied prefab retained `ShipInfo.ShipType = 29`. The clone workflow now sets this field to the new ship database ID; the installed and work MKII bundles have been set to 206 and structurally verified. The level-table registrations are also present: `FleetModelFactory` in `level5` and `level85`; `ProjectionFactory` and `ShipImageDataTable` in `level5`, `level6`, `level7`, `level8`, `level85`, and `level9`. Research unlock rows are present in the level tables, but campaign saves retain their research state from campaign creation.

On 2026-11-25 the MK2 froze the game while a battle loaded. The log showed `The AssetBundle 'Memory' can't be loaded because another AssetBundle with the same files is already loaded.`, then `Asset bundle for colonialmercurymk2 is null!` and an unhandled `FileNotFoundException` from `AssetBundleManager.GetAssetBundle`. The game kept running at full CPU but stopped writing to its log. Inside a bundle, the files are named `CAB-<32 hex>` (the serialized file) and `CAB-<32 hex>.resS` (streamed mesh and texture data). The serialized file points at the second as `archive:/CAB-<hex>/CAB-<hex>.resS` in each Mesh's and Texture2D's `m_StreamData.path`. Unity refuses to load a bundle whose CAB names are already loaded. The copy kept the Mercury's `CAB-8cc2d8dacddd97376527ac9db49b218f`, so it failed whenever the Mercury bundle was loaded first. The clone code now gives a copy new CAB names: the node names, plus every `CAB-<hex>` string inside the serialized file (a same-length swap, so string lengths and offsets stay valid). The new hash is the MD5 of the new bundle name and the old hash, so rebuilding the same clone gives identical bytes. The `(FleetShip Save file validation) ... 6 slots instead of 8` line logged before the freeze is the save loader correcting the munitions slot count, not an error.

### Localisation and in-game screen layout

The game stores numeric localised strings in Unity TextAssets inside `BSG_Data/resources.assets`. Each row contains an ID, display text, and an optional translator note, separated by pipes. Ship `descriptionID` and `descriptionShortID` reference the `default` table. `DescriptionHeaderID` and `DescriptionBodyID` reference `blueprint_descriptions`.

The editor's **Localisation** tab opens the strings referenced by an existing ship and can allocate new IDs for future ship records. It writes to the working `BSG_Data/resources.assets`, preserves other assets, and verifies that edited strings can be read back. New IDs use the English text in any language left blank.

The expanded slot UI uses `UIWidgetList.listScaleMode`. In the inspected `level5` and `level85`, construction and research munition/squadron lists used `None` (0), while their child grid layouts were already configured to wrap to additional rows. Setting these lists to `TopToBottom` (1) lets their containers grow with the rows. In `sharedassets5.assets`, ship cards use a horizontal layout for the upper slot icons and a one-row grid for the lower icons. The tool disables the horizontal layout, adds a fixed eight-column grid above, changes the lower grid to four columns, and enables vertical content sizing so the lists wrap instead of stretching across the card. It also enables vertical content sizing on the ship list inside its scroll view. In `level9`, the battle `ShipSquadronlMultiImageWidgetList` grid has four columns and 37.5 units of height; Mercury's eight squadron icons need two rows, so the tool raises this panel to 75 units. The commander detail panel's `SkillsWidgetList` uses a vertical `ScrollRect` and a clipping mask on its content panel. Its `TopToBottom` list mode must be preserved in the final serialized write; an earlier write order reset it to `None`, collapsing the layout and making skill entries overlap profile fields. The corrected `level5` and `level85` are installed in GOG and both work trees with backups. The saved asset files were reloaded and confirmed to retain `listScaleMode=1` and their scroll references; final in-game scrolling still needs visual confirmation.

The installed Mercury has a `DeployPlatingModule`, but its ship database record has `PlatingSupplyRequired = 0`. The game initializes the module's battle stock from the campaign `FleetShip.StockData.PlatingAvailable` value and persists the remaining stock after a battle. This explains why the prefab's plating capacity does not ensure a campaign ship enters battle with supply. Celestra's stock record uses 400. Mercury's current prefab capacity is 400,000, so matching that value in the ship database would allow a full refill but would also create a much larger campaign supply requirement; existing campaign stock may need resupply before the next battle.

### Donor abilities and menu capacity

The donor-based options use local game assets. Defender supplies turnaround repair, technical support, and reinforcement. Celestra supplies targeted munition resupply and plating. Turnaround repair needs a suitable docking bay. The Defender's Raptor-related actions need an appropriate bay and squadron. Resupply has two stock buttons in its submenu. The tool uses the existing Abilities submenu where available and checks for a free position. Serialized component checks establish that links are present in the output, while skirmish testing establishes whether the game executes the action.
